# 业务领域约束

OpenScout Agent 的业务目标是帮助开发者根据学习目标检索、分析和筛选开源项目，并生成可解释评分与学习路径。

## 1. 领域边界

- 用户目标：自然语言学习目标、时间约束、技术偏好、候选项目范围。
- 项目画像：GitHub repo metadata、README、Release、目录摘要和缓存信息。
- 项目评分：规则评分是最终分数来源，LLM 只负责解释和总结。
- 学习计划：基于用户目标和项目画像生成每日任务，不应伪造不存在的项目模块。
- Agent Trace：记录执行过程用于复盘，不作为业务决策的唯一来源。

## 2. 业务不变量

- 项目评分必须可解释，分数项应能追溯到 metadata、README、目录结构或规则命中证据。
- LLM 不得覆盖规则评分；如果 LLM 输出与规则结果冲突，应以规则评分为准并在回答中解释。
- GitHub API 失败、限流或模型不可用时，系统应能在 mock 数据或缓存数据下继续演示核心链路。
- 批量项目采集允许部分失败，响应中必须保留失败项目和失败原因。
- Trace 只能保存摘要和脱敏字段，不保存完整密钥、完整敏感配置或大体积原文。

## 3. 评分规则

评分维度计划包括：

- 活跃度：更新时间、release、issue 活跃情况。
- 文档完整度：README 长度、安装说明、示例、测试、文档目录。
- 技术匹配度：语言、topics、README 关键词与用户目标匹配。
- 学习友好度：examples、quickstart、demo、模块清晰度。
- 简历价值：工程完整度、生态影响、可复现性、技术含金量。

## 4. 外部 API 与并发

- GitHub API 调用必须设置超时，不允许无限等待。
- 真实 API 模式必须支持 `GITHUB_TOKEN`，未配置 Token 时应提示限流风险。
- 遇到限流、403、429 或 secondary rate limit 时，不应盲目重试。
- worker pool 的并发数必须可配置，默认值保守。
- Redis 缓存必须有 TTL，缓存 key 命名要稳定且可追踪。
